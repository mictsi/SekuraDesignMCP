Loading, empty and error states

The states a screen spends most of its unhappy life in. Each one below is the real component, not a picture of it.

One rule covers most of this page

A state must say what happened, why, and what to do next. Copy that only manages the first of the three — “Something went wrong” — leaves the reader with nothing to act on.

Errors

Sorted by blast radius. The bigger the failure, the more room it gets — but a page-level error is never used for a problem confined to one field.

Field level — the user can fix it here

The message sits with the field, is referenced by aria-describedby, and says what a valid value looks like. “Invalid input” describes the verdict, not the fix.

Prefixes every task number.

Use 2 to 6 capital letters or digits, with no spaces. For example, WEB.

Section level — one panel failed, the page did not

Contain the failure. Replacing the whole page because one widget's request failed throws away everything else that loaded correctly.

Activity could not be loaded

The activity service did not respond within 10 seconds. Everything else on this page is up to date.

Partial success — the hardest one to write

A bulk action that half worked is neither a success nor a failure, and reporting it as either is a lie. Give both numbers, and let the user act on the failed subset alone.
